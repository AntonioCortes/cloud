Shared Libraries y Groovy Avanzado

Si tu empresa tiene 200 repositorios de microservicios, copiar y pegar 200 veces el mismo `Jenkinsfile` es un desastre de mantenimiento. Si cambia la política de despliegue, tendrías que modificar 200 archivos. Aquí es donde brillan las Shared Libraries.

Estructura Real de una Shared Library

Una Shared Library es un repositorio de Git aparte (ej: `jenkins-shared-library.git`) que Jenkins clona dinámicamente antes de cada build. Su estructura experta es:


(root)
+- src/                     # Código Groovy orientado a objetos (Clases)
|   +- org/empresa/cicd/
|       +- NotificadorSlack.groovy
+- vars/                    # Variables globales (Funciones que puedes llamar en tu Jenkinsfile)
|   +- buildMicroservicio.groovy
|   +- escanearSeguridad.groovy
+- resources/               # Archivos estáticos
|   +- plantillas-k8s.yaml

Implementando el DSL (Domain Specific Language)

Dentro de `vars/buildMicroservicio.groovy`, escribes todo tu Pipeline Declarativo enorme. Luego, en los 200 repositorios de los desarrolladores, su `Jenkinsfile` se reduce a una sola línea mágica:


// Importa la librería (el nombre se configura en Jenkins global)
@Library('mi-empresa-lib') _

// Llama a la función global. ¡Esto ejecuta todo el pipeline estándar!
buildMicroservicio(
    nombre: 'api-pagos',
    lenguaje: 'java',
    desplegarEnProd: true
)

Ejecución en Paralelo (Parallel)

Para reducir el tiempo total de compilación, ejecuta tareas independientes al mismo tiempo usando el bloque `parallel`.


stage('Testings y Seguridad') {
    parallel {
        stage('Unit Tests') { steps { sh 'make test' } }
        stage('SonarQube') { steps { sh 'sonar-scanner' } }
        stage('Cypress E2E') { steps { sh 'npm run e2e' } }
    }
}
