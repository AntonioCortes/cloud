ConfigMaps y Secretos

Uno de los principios de diseño más importantes en la ingeniería de software moderna (como la metodología de los 12-Factor App) es la estricta separación de la configuración y el código fuente. Tu aplicación no debería tener "quemados" (hardcoded) detalles como la URL de la base de datos o claves de acceso dentro del código.

Kubernetes ofrece dos objetos de primera clase para inyectar configuración en tus contenedores de forma dinámica: ConfigMaps y Secrets.

1. ConfigMaps: Configuraciones No Sensibles

Un ConfigMap se utiliza para almacenar datos de configuración que no son confidenciales. Se guardan en texto plano en forma de pares clave: valor.

¿Qué tipo de cosas guardamos en un ConfigMap?

  • URL de servicios (ej: URL_BACKEND=http://mi-servicio-backend)
  • Niveles de Logging (ej: LOG_LEVEL=DEBUG)
  • Archivos de configuración completos (ej: un archivo `nginx.conf` completo para inyectarlo en un Pod de Nginx).

Ejemplo de ConfigMap

# archivo: mi-configmap.yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: configuracion-app
data:
  # Variables simples
  TEMA_UI: "oscuro"
  LIMITE_USUARIOS: "100"
  
  # También puedes guardar archivos enteros aquí
  config-especial.json: |
    {
      "moduloActivo": true,
      "reintentos": 5
    }

2. Secrets: Protegiendo lo Sensible

Los Secrets son casi idénticos a los ConfigMaps, con la única diferencia de que están diseñados para guardar información confidencial, como contraseñas, tokens de API o claves SSH.

⚠️ Advertencia Crítica de Seguridad: Por defecto, Kubernetes NO encripta los Secrets en la base de datos (etcd) ni en los archivos YAML. Solamente los codifica en base64 para que no se lean accidentalmente a simple vista. Cualquier persona que tenga acceso al clúster (o al archivo YAML si lo subes a GitHub) puede decodificarlos fácilmente.

Para producción, siempre debes activar la encriptación "en reposo" en tu clúster de K8s, o utilizar gestores de secretos externos avanzados como HashiCorp Vault o AWS Secrets Manager integrados con K8s.

Ejemplo de Secret

# archivo: mi-secreto.yaml
apiVersion: v1
kind: Secret
metadata:
  name: credenciales-db
type: Opaque # Tipo estándar
data:
  # Estos valores deben estar codificados en base64 previamente
  # echo -n 'usuario_root' | base64
  username: dXN1YXJpb19yb290
  # echo -n 'P@ssw0rd123' | base64
  password: UEBzc3cwcmQxMjM=

3. ¿Cómo consumen los Pods esta configuración?

Una vez que tienes el ConfigMap o el Secret creado en el clúster (usando kubectl apply), puedes inyectar esos datos en tus Pods (o Deployments) de dos maneras principales:

Método A: Como Variables de Entorno (El más común)

Puedes decirle al Pod que tome un valor del ConfigMap y se lo pase a tu aplicación NodeJS, Python o Java como una variable de entorno normal del sistema.

# Fragmento de un Deployment inyectando configuración
      containers:
      - name: mi-app
        image: mi-app:v1
        env:
        - name: TEMA_DE_LA_APP
          valueFrom:
            configMapKeyRef:
              name: configuracion-app # Nombre del ConfigMap
              key: TEMA_UI            # Clave específica

Método B: Como Archivos en un Volumen

K8s puede tomar el contenido del ConfigMap o Secret y crear archivos físicos temporales dentro del contenedor. Si inyectas un Secret de esta forma, K8s crea los archivos en la memoria RAM del contenedor, no en el disco duro, por motivos de seguridad.

# Fragmento: Montar un configmap como archivo
      containers:
      - name: mi-app
        image: mi-app:v1
        volumeMounts:
        - name: volumen-config
          mountPath: /etc/configuracion # Carpeta dentro del contenedor
      volumes:
      - name: volumen-config
        configMap:
          name: configuracion-app

Utilizar ConfigMaps y Secrets asegura que tu imagen de contenedor sea inmutable y genérica. La misma imagen que despliegas en el entorno de Pruebas es la que despliegas en Producción; lo único que cambia son los ConfigMaps y Secrets que le conectas en cada entorno.
