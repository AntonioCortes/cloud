Arquitectura del Clúster

Para entender verdaderamente Kubernetes, necesitamos saber qué ocurre "bajo el capó". Un clúster de Kubernetes no es una caja mágica; es un conjunto de máquinas (físicas o virtuales) que asumen dos roles muy específicos: el Plano de Control (Master Nodes) y el Plano de Datos (Worker Nodes).

1. El Plano de Control (Control Plane)

El Plano de Control es el cerebro del clúster. Toma las decisiones globales (por ejemplo, planificar cuándo arrancar un nuevo contenedor) y detecta y responde a los eventos del clúster (como arrancar un contenedor de reemplazo cuando uno falla). En producción, los componentes del plano de control suelen ejecutarse en máquinas dedicadas llamadas Master Nodes.

Los componentes principales del Plano de Control son:

Componente ¿Qué hace? (Explicación sencilla)
kube-apiserver Es la puerta de entrada principal. Cuando escribes `kubectl get pods`, tu ordenador habla con el API Server. Todo en K8s, desde los trabajadores internos hasta nosotros, se comunica a través del API Server.
etcd Es el "disco duro" del cerebro. Es una base de datos clave-valor ultra rápida y altamente disponible. Aquí se guarda *absolutamente toda* la configuración y el estado actual del clúster. Si pierdes el etcd, pierdes el clúster entero.
kube-scheduler El planificador. Su único trabajo es vigilar los nuevos contenedores que piden ser ejecutados y decidir en qué máquina (Worker Node) específica ponerlos basándose en la CPU y RAM disponibles, reglas de afinidad, etc.
kube-controller-manager El "vigilante". Son múltiples procesos corriendo en bucle infinito que observan el estado actual y lo comparan con el estado deseado. Si pides 3 réplicas de una app y detecta que solo hay 2 vivas, el Controller Manager lanza la orden para crear otra.

2. Nodos Trabajadores (Worker Nodes)

Si el Plano de Control es el director de la orquesta, los Worker Nodes son los músicos. Son las máquinas que realmente ejecutan el código de tu aplicación. Un clúster puede tener desde un solo Worker Node (como en Minikube) hasta decenas de miles.

Cada Nodo Trabajador tiene 3 componentes fundamentales:

  • kubelet: Es el agente o "capataz" del nodo. Recibe órdenes del API Server (ej: "Asegúrate de que este contenedor de Nginx esté corriendo aquí") y se encarga de cumplirlas. Monitorea constantemente los contenedores y reporta su estado de vuelta al cerebro.
  • kube-proxy: El guardián de las reglas de red. Mantiene la comunicación de red en tu clúster. Se encarga de actualizar las reglas del firewall local del servidor (usualmente usando iptables en Linux) para que el tráfico de red llegue al contenedor correcto, incluso si este contenedor cambió de servidor.
  • Container Runtime: Es el software responsable de ejecutar los contenedores reales. En el pasado, esto solía ser únicamente Docker, pero hoy en día el estándar de la industria es containerd o CRI-O. El `kubelet` le dice al runtime "descarga esta imagen y ejecútala".

Resumen del Flujo

Imagina que quieres desplegar tu aplicación web. Este es el camino que recorre tu orden:

  1. Escribes tu archivo YAML definiendo tu estado deseado y ejecutas kubectl apply -f archivo.yaml.
  2. El API Server recibe la petición, la valida y guarda ese "deseo" en la base de datos etcd.
  3. El kube-scheduler detecta que hay un nuevo contenedor esperando ser asignado, revisa qué Nodo Trabajador tiene recursos libres y toma una decisión. Guarda esta decisión de vuelta en el API Server.
  4. El kubelet del Nodo Trabajador elegido se da cuenta de que le han asignado trabajo. Habla con su Container Runtime (ej. containerd) para descargar la imagen y arrancar el contenedor.
  5. El kubelet le avisa al API Server: "¡Trabajo completado, el contenedor está corriendo!".
