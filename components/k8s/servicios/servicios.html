Servicios e Ingress (Redes en K8s)

Hasta este punto, sabemos cómo crear una aplicación asegurada mediante un Deployment, lo cual nos generará varios Pods. Pero aquí surge un problema gigantesco de red: Los Pods son efímeros y sus direcciones IP cambian constantemente.

Si tienes un Frontend que necesita comunicarse con tu Backend, no puedes decirle al Frontend "conéctate a la IP 10.244.1.5", porque si ese Pod de Backend muere y es reemplazado por otro, el nuevo tendrá una IP diferente (ej: 10.244.2.8) y tu Frontend se romperá. Aquí es donde entran los Services (Servicios).

1. ¿Qué es un Service en Kubernetes?

Un Service es una abstracción lógica que agrupa un conjunto de Pods (normalmente usando selectores de etiquetas, igual que los Deployments) y les asigna una dirección IP estática y un nombre DNS único que nunca cambian durante la vida del Servicio.

El Service actúa como un balanceador de carga interno. Tu Frontend siempre hará las peticiones a la IP estática del Service (o simplemente a su nombre DNS, como http://mi-backend). El Service recibirá la petición y la redirigirá a uno de los Pods vivos del backend, sin importar qué IPs tengan en ese momento.

2. Los 3 Tipos Principales de Servicios

Dependiendo de desde dónde necesites acceder a tus Pods, elegirás un tipo de Servicio u otro:

Tipo de Servicio Caso de Uso (Cuándo usarlo)
ClusterIP (Por defecto) Expone el servicio únicamente de forma interna en el clúster. Úsalo para comunicación entre tus propios microservicios (ej: el Frontend hablando con el Backend, o el Backend con la Base de Datos). Nadie de fuera de internet puede acceder a él.
NodePort Abre un puerto estático (entre 30000 y 32767) en la IP de cada Worker Node del clúster. Permite acceder al servicio desde fuera del clúster (ej: desde el navegador de tu portátil) visitando IP_DEL_NODO:NodePort. Es útil para desarrollo local (como vimos en Minikube), pero no se recomienda para producción pura.
LoadBalancer El método estándar en producción para exponer a internet. Si tu clúster está en la nube (AWS, Azure, GCP), este servicio pedirá al proveedor de la nube que genere un Balanceador de Carga externo (con una IP pública) que redirija el tráfico hacia tu clúster.

3. Definiendo un Service (ClusterIP)

Veamos un ejemplo de cómo crear un servicio que expone nuestro Backend para que solo la base de datos o el frontend interno puedan hablar con él.

# archivo: mi-servicio-interno.yaml
apiVersion: v1
kind: Service
metadata:
  name: servicio-backend
spec:
  type: ClusterIP # Este es el valor por defecto si no lo pones
  selector:
    app: backend # ¡Magia! Este servicio ruteará tráfico a todos los Pods con esta etiqueta
  ports:
  - protocol: TCP
    port: 80       # El puerto del Servicio en sí mismo
    targetPort: 3000 # El puerto en el que la aplicación (NodeJS/Python) está escuchando dentro del Pod
Al crear esto (`kubectl apply -f mi-servicio-interno.yaml`), K8s registrará internamente el DNS 'servicio-backend'. Cualquier otro Pod puede hacer 'curl http://servicio-backend:80' y llegará mágicamente al puerto 3000 de un Pod sano.

4. Ingress: El Guardia de Seguridad y Enrutador de Internet

Si usas un LoadBalancer por cada microservicio que quieres exponer a Internet, tu proveedor de nube te cobrará un Balanceador de Carga por cada uno (lo cual es carísimo). Además, el LoadBalancer es de capa 4 (rutas por IP y puertos, no entiende de rutas HTTP).

Para exponer aplicaciones web complejas, usamos el objeto Ingress.

Ingress opera en la Capa 7 (HTTP/HTTPS). Actúa como un enrutador inteligente y proxy inverso en la entrada de tu clúster. Usualmente necesitas instalar un "Ingress Controller" (como Nginx Ingress) para que funcione.

¿Qué nos permite Ingress?

  • Tener un solo LoadBalancer (una sola IP pública) y pagar menos.
  • Enrutar el tráfico basado en la URL. Ej: Si el usuario entra a misitio.com/api, Ingress redirige el tráfico al Service del Backend. Si entra a misitio.com/web, lo redirige al Service del Frontend.
  • Terminación de SSL/TLS (poner certificados HTTPS para que la web sea segura).
# Ejemplo de reglas de Ingress
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: mi-enrutador-principal
spec:
  rules:
  - host: www.miempresa.com
    http:
      paths:
      - path: /api
        pathType: Prefix
        backend:
          service:
            name: servicio-backend
            port:
              number: 80
      - path: /
        pathType: Prefix
        backend:
          service:
            name: servicio-frontend
            port:
              number: 80
Reglas de Ingress: Si el dominio coincide y la ruta es /api, ve a los Pods del backend. Si es la ruta raíz /, ve a los Pods del frontend.

En resumen: Deployments gestionan Pods. Services dan una IP fija a un grupo de Pods. Ingress enruta el tráfico de internet HTTP hacia los Services correctos.
