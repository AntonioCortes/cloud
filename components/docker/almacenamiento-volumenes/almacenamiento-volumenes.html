Almacenamiento y Persistencia de Datos

Los contenedores tienen una capa final de Lectura/Escritura. Sin embargo, esta capa es efímera, sujeta al ciclo de vida del contenedor y su rendimiento en disco es muy bajo debido a la sobrecarga del controlador de almacenamiento (Storage Driver). Para bases de datos y archivos permanentes, utilizamos técnicas que evaden el Storage Driver.

Tipo Mecanismo Interno Uso Experto
Volumes Manejados directamente por Docker (`/var/lib/docker/volumes/`). Aislados del resto del SO host. Producción. Backups fáciles y soporte para "Volume Drivers" (ej. conectar almacenamiento de la nube NFS/EBS directamente al contenedor).
Bind Mounts Mapeo directo de un inodo del host al contenedor. El contenedor puede sobrescribir archivos del host si no se limita. Desarrollo. Para ver cambios de código en tiempo real sin recompilar la imagen.
tmpfs Almacenamiento montado exclusivamente en la RAM. Nunca se escribe en el disco físico. Seguridad extrema. Para guardar claves API o tokens de sesión que no deben persistir jamás tras un reinicio.

Volumes Anónimos vs Nombrados

Si usas `-v /var/lib/mysql` sin especificar un origen, Docker crea un volumen anónimo con un hash alfanumérico ininteligible. Siempre usa volúmenes nombrados (`-v db_data:/var/lib/mysql`) para poder referenciarlos fácilmente en el futuro en otros contenedores o migraciones.
