Seguridad y Hardening en Docker

Los contenedores no son cajas mágicas de seguridad impenetrable. Dado que comparten el kernel del host, una escalada de privilegios en el contenedor puede comprometer todo el servidor. El Hardening es obligatorio.

1. Rootless Mode

Por defecto, el demonio de Docker corre como root. Un atacante que vulnere el demonio obtiene control total. El modo Rootless ejecuta tanto el demonio como los contenedores dentro de un User Namespace, engañando al proceso para que se crea root dentro del contenedor, pero siendo un usuario sin privilegios en la máquina host.

2. Drop Capabilities (Eliminar Privilegios de Linux)

El kernel de Linux divide los privilegios de root en "Capabilities" (ej. CAP_NET_ADMIN para modificar redes, CAP_SYS_TIME para cambiar la hora). Docker por defecto otorga varias, pero la mejor práctica es quitarlas todas (drop all) y añadir solo las estrictamente necesarias.


# Desplegando máxima paranoia de seguridad
docker run -d \
  --name app-segura \
  --cap-drop ALL \
  --cap-add NET_BIND_SERVICE \
  --read-only \
  mi-app
El contenedor no puede ejecutar nada como root real, ni modificar su propio sistema de archivos (--read-only).

3. Imágenes Distroless y Escaneo

Las imágenes Alpine son populares, pero aún incluyen un gestor de paquetes (apk) y una shell (sh). Las imágenes Distroless (creadas por Google) no tienen nada más que las librerías necesarias para ejecutar tu aplicación. Sin shell, un atacante no puede ejecutar comandos incluso si inyecta código.
